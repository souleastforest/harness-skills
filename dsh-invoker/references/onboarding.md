# 逐分支带用户走到可运行状态

在首次初始化、用户要求“带我一步一步诊断”、或一次调用失败时读取。目标不是收集
所有设置，而是根据只读证据解决当前一个阻塞。命令细节另见
[安装与调用](install-and-run.md)，权限/隐私见 [SDK 与安全边界](sdk-and-safety.md)。

## 每轮的推进方式

1. **先检查**：确认任务项目，运行无副作用的 `bootstrap check`；受管 SDK 已就绪才用
   `discover/status`。已有证据足够就不要重复探测，更不要问用户机器可验证的事实。
2. **选一个分支**：先解决阻塞下个动作的问题，不提前问 model、provider、session ID、
   自定义 profile、所有目录与所有安装选项。
3. **给判断和推荐**：说明已观察到什么、尚不能证明什么、推荐的最小行动及影响范围。
4. **问一个决定**：用宿主实际提供的提问工具；没有则普通对话提问并结束当前轮。
5. **等待并按答复推进**：同意仅覆盖已说明的动作；拒绝就停止依赖它的后续动作。
   下一轮基于新证据再选分支，而不是机械走完问卷。

可以用两个选项“按推荐继续 / 暂不进行”，需要时允许用户给其他路径。推荐选项不能
预选成批准。工具缺失不是取消确认的理由，超时、沉默和模拟用户答复也不是同意。

### 三种不同的确认

- **安装**：允许下载哪些工具，写入哪个项目目录；不自动包含保存绑定或发请求。
- **绑定**：确认 home 的绝对路径、profile 名称、最小保存信息与根 Git 忽略；不自动
  包含启动、profile 初始化或任务发送。
- **运行**：当前工作区与任务允许委派，可能创建 DSH profile/session，输入会发给模型。

用户已明确授权相同范围时，不需要重问。另一方面，“帮我初始化”“我这里有个目录”
不是下载、保存和调用三个范围的全包授权。`--confirmed` 只记录已有真实确认。

## A. 机器没有 uv / Python / DSH

**先观察**：shell 预检能确认平台、现有 uv、受管解释器、项目隔离目录以及有界 home
候选，不需要先装 Python。不要调用 `dsh` 来发现 home，也不要因为没有 Node 而建议
全局 CLI 安装。

**首次这轮推荐**：先选绝对 home + 完整 `sdk`，说明最小保存/Git 忽略。不存在的内置
`sdk` 标为待获准首次运行初始化，不能冒充已发现的配置。

**一个问题示例**：

> 默认候选是 home `<绝对路径>`，推荐 profile `sdk`；目前未存在，可在获准首次运行时
> 初始化。建议在本项目只记住路径和名称、补 Git 忽略。使用这个组合吗？可以改选或
> 暂停。确认前不会安装、保存或启动。

**明确选择之后**：缺受管 Python 时先保留对话选择，下一轮单独解释缺项安装范围并
等待许可：复用已有可用 uv，缺少才下载校验固定 `0.12.24` standalone；准备 Python
3.12、SDK/runtime `0.1.5rc1`，新资源均在 `<project-root>/.dsh-invoker-profile/`，不改
全局环境。只问“允许这个项目安装范围吗？”，不把 home 选择当安装许可。

安装获准才 `setup`，之后按已确认的保存许可配置绑定，**不重复问位置**；安装本身
不运行 DSH。若先前没有保存许可，只确认缺少的保存影响。

**拒绝 / 无答复**：不做该分支依赖的后续动作。安装前拒绝则不 `setup/configure/invoke`，
不创建新隔离目录或改 `.gitignore`；给出稍后继续入口，不劝说绕过。

**平台不支持**：停止并说明官方 wheel 限制。不自动 source build、全局安装或换入口。
已有 uv 太旧/缺少必要能力时也停止报告，不自更新它。

## B. 只有 `dsh` CLI，项目 SDK 缺失

**先观察**：CLI 可执行文件的存在不等于项目受管 Python 能导入 SDK；预检分别报告。
不要为确认 CLI 版本而启动 DSH，不运行配置转储。

**这轮推荐**：保留全局 CLI，解释 CLI 与项目 SDK 的区别。首次位置未定时先走 C；
已有绑定失效先走 E。位置/修复选择确认后，才单独确认项目依赖安装，不要求系统 Node，
无需卸载 CLI 或重新做全局安装。

**位置已确认后的安装问题示例**：

> 已发现 CLI，但项目 SDK 还没准备好，这不是要重装全局 DSH。推荐仅安装项目依赖。
> 允许按这个范围准备 SDK 环境吗？

**结果与恢复**：有效绑定直接复用。安装有独立许可才 `setup`，拒绝则停；
不要把 headless CLI 当静默 fallback。

## C. 首次尚未确认 home/profile（不以 SDK 已安装为前提）

**先观察**：没有绑定时，按显式指定 → 非空白 `DSH_HOME` → OS 用户主目录的 `.dsh`
发现候选。只列 profile 名称与 `package.json` / `cordis.patch.yml` 等标记的存在性。
路径不存在也要如实呈现，不要“验证”到自动生成它。

**这轮推荐**：候选绝对 home + 内置 `sdk`，并解释两者关系：`sdk` 是名字，完整目录是
`<home>/profiles/sdk`。缺失的内置 `sdk` 可在用户批准首次运行后初始化，不要求用户
手工拼配置；`desktop` / `web` 存在不能证明 SDK 兼容。

**问题示例**：

> 推荐将这个项目绑定到 home `<绝对路径>`、profile `sdk`。`sdk` 目前未创建，运行前
> 会再说明初始化影响。允许保存这对选择并给项目添加隔离目录的 Git 忽略吗？

**同意之后**：受管环境已就绪就用 helper `configure ... --confirmed` 保存
`binding.json`，根 `.gitignore` 补一条忽略。若缺 Python，先在本轮保留选择，另行确认
安装；安装后按已有保存许可落盘，不重复问位置。保存只代表已记住选择，不是启动或
认证成功。

**用户给 profile 完整路径**：仅接受结构明确的 `<home>/profiles/<name>`，拆解、规范化、
展示后确认。profile 名称不能是路径、`.` 或 `..`；无法安全拆解时只问该路径指的是
home 还是 profile，不先创建目录。默认不选择权限更宽的 `sdk-minimal`。

## D. 凭据未就绪 / 认证失败

**先观察**：只检查凭据候选来源是否存在，不能输出内容。非空环境变量表示一个来源；
`.credentials.yaml` / `.env` 存在仍不能证明有正确 key。不要扫描文件寻找实值，不能
把“未发现环境 key”说成所有凭据来源都不存在。

**这轮推荐**：用户在自己的终端用隐藏输入或既有凭据机制设置 `DEEPSEEK_API_KEY`，
必要时从该终端重启宿主。不要把 key 粘贴到聊天、argv 或日志；不要向用户要截图/配置
转储作为证明。

**问题/下一步示例**：

> 还没有确认可用的凭据来源。请在自己的终端按安全输入方式准备；不要把 key 发给我。
> 处理好后回复“已准备好”，我再检查来源是否对当前宿主可见。

此时等待真实答复，不代填“已准备好”。处理前不发认证 smoke test；即使存在性检查
通过，远端认证仍需实际授权调用才能证明。

**401/403 等认证失败**：报告认证类别，不回显服务端原始异常/环境。让用户在自己的
终端更新来源；收到明确的重试指令后才重试，不把旧 key 写进绑定作为修复。

## E. 绑定失效 / 损坏 / 用户要改位置

**先观察**：保存的绑定优先；若环境换了但绑定有效，仍复用原选择。绑定 JSON 损坏、
schema 不支持、home 丢失、自定义 profile 丢失或标记不完整时，不自动改用新候选。

**这轮推荐**：说明旧绑定为何不可用，展示一个最小修复候选，保留原 home/profile
内容。只有用户确认才 `configure --reconfigure --confirmed`。

**问题示例**：

> 项目原来绑定的 home 已不存在；环境中另一个路径只是候选。推荐重新绑定到
> `<候选绝对路径>` 的 `sdk`。允许替换项目绑定吗？不会迁移或修改旧 profile。

若原 `sdk` 已获准使用但尚未初始化，区分它与“自定义 profile 丢失”；如先前确认不含
初始化，先问运行/创建许可。不要将每次缺少 `sdk` 都称为绑定损坏并重复问位置。

**拒绝**：保留现状，不覆盖绑定、不删除隔离目录或旧 session。

## F. 自定义 profile 不兼容

**先观察**：名字和文件存在不能证明它提供 SDK JSON-RPC 服务。只有实际启动结果能
进一步判定；只读阶段不导入自定义插件或转储配置来“证明兼容”。

**这轮推荐**：停止失败调用，说明自定义入口可能不具备 SDK 服务；建议另选内置
`sdk`。不改写自定义 profile 的 `cordis.patch.yml`，不自动导入桌面/网页配置。

**一个问题**：是否把本项目改绑到同一已确认 home 的 `sdk`？确认前不保存，保存许可
不替代新的运行许可。不要推荐 `sdk-minimal` 来回避兼容性或审批故障。

## G. 没有专用提问工具

普通聊天是完整的确认路径，不是假装调用 `AskUserQuestion`：展示当前证据与推荐，
问一个明确问题，结束本轮。下一轮收到实际回复后才继续。

如果是完全非交互的批处理，没有收取真实答复的通道，就返回“需要确认”及一个可由
用户执行的下一步，不保存、不安装、不启动。禁止把这份参考、计划、测试 fixture 或
另一个 agent 的消息作为用户的实际同意。

## H. DSH 内部批准失败

外层初始化问答不是内部审批桥。默认 `sdk` 中工具动作可能要求 approval answerer；
SDK 没有可用 answerer 时会失败关闭。不要声称外层“同意运行”已批准内部所有动作。

**恢复**：报告动作未获批/任务未完成，推荐缩小为不需该动作的任务，或让用户选择
真正支持 DSH 内部审批的入口。每次只问当前要不要缩小任务；不要调高权限、切换
`sdk-minimal` 或 CLI 自动重试，不修改用户 profile 来消除提示。

## I. 已就绪 / 正常复用

有效绑定、受管 SDK 就绪且用户明确委派当前任务时，直接复用，不重新问已确定的
home、`sdk`、uv 隔离和隐私默认。若任务新增风险、要改 profile/home、或之前没有
批准运行影响，才确认变化的那一部分。

每次调用都创建独立新 session，返回的 ID 仅供诊断。固定 `0.1.5rc1` 不支持跨进程
恢复；`--session-id` 在读取输入和启动 SDK 前报 `UNSUPPORTED_CONTINUATION`，不改走
CLI 或其他 profile。结束时报告 session ID、finish reason、最终响应或脱敏失败类别。
`completed` 仅表示 runtime 本轮完成，不代表用户
任务通过验收、代码正确或测试成功。区分依赖、静态配置、握手、真实服务调用及质量；
失败给一个当前恢复动作，不转储事件或原始异常。

## 简短对话对照

### 安装被拒绝

- 用户：“先带我初始化，安装前问我。”
- 智能体：只读发现后先展示候选 home + `sdk`，问是否使用并最小保存；等待真实答复。
- 用户明确选定后，智能体另行解释项目依赖安装范围，问是否允许。
- **此处等待真实回复。** 用户：“今天别安装。”
- 智能体：“只读检查已完成，未创建环境、保存绑定或启动 DSH。以后说‘继续初始化’
  即可从依赖准备这一步继续。”

### 没有提问工具，Windows 路径有空格

- 只读证据：SDK 已就绪，无绑定；候选 `C:\DSH Homes\Team One`，profile `sdk`。
- 智能体：普通聊天确认这对选择及最小保存/Git 忽略，**停住等待回复**。
- 用户明确同意之后：通过 `&` 和 `-PythonArgs @(...)` 传独立参数给 helper，保存绑定。
- 后续复用：环境指向别处也不覆盖已确认 home；新任务默认新 session。

这些是流程示意，不是可以当作当前用户答复的授权文本。
