# 软件开发流程

开发、修复或重构软件时按需读本页。沿用项目已有的规格、任务和检查方式，补齐本轮缺少的部分。流程深度依 [任务复杂度](task-complexity.md) 判断；局部、路径清楚的修改可以直接实施并检查。

RePPIT 包含研究、提出方案、计划、实施和测试。已有材料可以满足其中的工作，不必重新写五份文档。既有授权覆盖本轮时连续推进；需要用户决定的新取舍按主技能带回讨论。

## 研究 Research

从请求涉及的入口开始，查清当前行为、相关调用、项目约束和可用的验证条件。优先回答会影响实现的问题，例如数据在哪里进入、哪些调用者依赖旧行为、如何观察修复是否生效。对陌生依赖核对当前文档。

研究完成时，应能指向相关文件或其他证据，说明拟改位置与理由，并列出仍会改变方案的未知。用定向调查或范围内的小实验解决这些未知；信息不足时标明假设。用户只请求研究时，交付发现与方案即可。

发现问题范围比预期小，就缩短后续流程。发现数据迁移、权限变化或难以回退的行为，即使只改一处，也补足相应验证和恢复安排。

## 提出方案 Propose

复用已经确认的路线。存在会影响结果的不同做法时，比较它们的用户体验、改动范围、维护成本和验证条件，再给出推荐及其前提。技术选择能够依据现有约束解决时，由助手处理；涉及新的范围、代价或用户偏好时，带回具体选择。

方案足够继续的依据是，路线能够实现本轮目标，影响路线的未知已解决或有可接受的处理办法。只有一条合理路径时，说明依据即可。

## 计划 Plan

把验收要求对应到实现步骤和验证方式，复用现有任务记录。短任务可在对话里说明，跨阶段工作更新项目的权威计划。每个任务写清预期产物、前置依赖、允许修改的范围，以及怎样判断完成。

此时就确定如何验证。例如修复导出错误，应准备能触发错误的输入和正确输出的判断依据；界面改动则需要观察实际界面。需要数据、设备、服务或权限的验证，提前确认能否执行。

从用户要求和现有契约确定输入范围与预期行为，区分已确认的边界和实现时的假设。所选实现或库函数只覆盖其中一部分时，补齐要求的行为；不能通过备注自行缩小交付范围。

执行者能从计划找到输入、开始工作并核对结果，就可以实施。若用户只授权研究或计划，到对应产物交付时结束；实施授权不会因计划写完而自动产生。

## 实施 Implement

按依赖顺序完成可验证的小段改动。实现期间出现新证据，就更新受影响的计划和验证方式；发现会改变用户选择的问题，暂停相关部分，继续独立且已授权的工作。用户中途改意时沿用主技能的处理规则。

范围内的常规检查和修复连续完成。把影响后续工作的失败尝试与原因留在现有记录中，避免接手者重试同一路径。涉及多人或代理时，给每位执行者明确的文件或职责范围，并适应共享工作区中的其他修改。

实施完成的依据是约定行为已有对应产物，剩余偏差能够明确指出。代理自报完成后仍需审阅产物与证据。团队编排依 [团队编排模式](team-orchestration.md) 显式启用；任务复杂度不自动启用该模式。

## 测试 Test

按计划检查实际行为，完成项目要求的检查及与改动相关的回归。验证可以穿插实施；代码检查、运行测试和人工观察分别支持不同结论。

按需求选择正常、边界和失败输入，至少覆盖会区分需求与实现假设的情况。不要只从已写好的实现反推测试，再用这些测试声称整个输入范围都已支持。

围绕失败修复授权范围内的问题，再复核受影响项。检查通过后，只有新改动、失败或尚未解决的疑点才需要扩大或重复测试。结果依赖特定环境时写明条件；未能运行的检查保留为未验证，并说明缺少什么。

收尾时将验收要求与实际证据对应起来，说明完成内容、已知限制和未完成项。发布、部署等动作沿用它们各自的授权范围；本页可独立执行，Superpowers 和 Matt 均为可选来源或接入。

## 分阶段和交接

依赖多、工作跨会话或接手者变化时，按可验收的任务或阶段切分。每阶段只补足该阶段需要的研究、方案和计划，完成后再决定下一阶段。选择任务完成、方向变化或需要换人接手的时点保存材料；上下文长度只能提示检查交接需求，不设统一百分比门槛。

沿用项目已有交接位置，保留以下接续信息。

- 本轮目标、已授权范围、已定决定及仍需用户决定的事项。
- 当前工作位置、适用修订与未提交改动，产物和原始证据的路径。
- 实际完成的验证及结果、失败尝试、环境限制和剩余依赖。
- 下一项可执行任务、所需输入、完成条件与停止条件。

接手者先核对材料和当前状态的差异，再继续有效的授权。只携带下一任务需要的上下文，保留回查原始材料的入口；简单任务的结果可留在对话中。
