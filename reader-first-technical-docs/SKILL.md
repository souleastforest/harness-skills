# 面向读者的技术文档

先读读者需要完成的工作和现有事实，再选择篇幅与文档形态。保留项目原有含义、授权
边界和验证结论；把它们写成读者能理解、能操作、能判断结果的说明。

## 确定这篇要帮助谁

1. 用一小段说明读者是谁、将得到什么结果、需要哪些已有条件。
2. 选择主线：教程带着完成一个过程，概念页建立模型，操作页解决一个具体问题，
   参考页供查字段和约定，背景页解释方法与取舍。短文可合写，长文按阅读目的分开。
3. 入口给出有理由的阅读分流，如“要理解这些名字的含义，读……；要开始一次试跑，读……”。

## 让读者跟得上正文

- 第一次使用名词时先说它在系统中做什么，再括注英文或代码名。定义交代谁使用、
  包含什么、解决什么问题。后文保持同一称呼，英文用于连接代码和记录。
- 先解释对象与关系，再介绍字段、哈希和版本号。用一个贯穿例子展示概念怎样参与工作。
- 标题表达动作或读者的问题，例如“准备新环境”“检查它是否装载”“出现失败时怎么办”。
- 一段回答一个问题。句子沿“对象 → 当前行为 → 原因 → 下一步”推进，避免把多个
  阶段、限制、编号和证据堆在一句话里。流程箭头只能在解释过各步骤后作辅助。
- 用自然的中文说明行动与目的；在真正需要准确标识时再出现 task ID、路径和 API 名。

## 写出能实践的步骤

1. 说明从哪个目录开始、要创建还是修改哪个文件，以及本步目的。
2. 给出真实存在的最小动作或命令。占位符说明如何替换；尚未实现的入口明确指出缺口。
3. 写出读者应在哪里看到什么结果，再解释这个结果证明了什么。
4. 就近说明常见失败的症状、可能原因、检查和修复动作。
5. 让下一步接续本步产物。高级分支在需要时给一两句解释并链接专页。

命令只是实践的一种形式。人工检查、选择输入、提取经验同样应写清输入、动作和结果。
示例输出标明是示意还是实测，保留“文件已准备、实际装载、行为发生、质量通过”之间的区别。
只有明确帮助读者理解概念时，才加入受控的失败或对照例子。

## 整理已有文档

- 为每项现役规则保留一个权威位置，其他页面用带理由的链接接续。
- 当前状态放在任务台账或当前检查点；教程讲过程，不累计每次实验后的“最新进展”。
- 先核对引用和证据，再归档被替代的路线与历史原文。保留来源修订、旧路径和哈希；
  被冻结证据引用的内容不全局改写，旧入口需要兼容时留简短指路页。
- 技术准确性与可读性一起检查：保留必要的权限、质量、失败和计量约定，将细节放在
  发生问题的位置或参考页。按真实材料修正过时说明，不因“删得更短”丢掉有效知识。

## 交付前按读者视角检查

读者能否说出这一页要做什么、每个首次出现的名词指什么、现在从哪里开始、怎样看出
一步已经完成、失败该查哪里、接着读哪页？再检查命令、局部链接、源码依据和历史状态。
篇末给出紧接当前成果的下一步。
